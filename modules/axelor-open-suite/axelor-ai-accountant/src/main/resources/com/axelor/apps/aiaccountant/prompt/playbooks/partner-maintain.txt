#version 2
[Playbook: CREATE or CHANGE a supplier]
GOAL: the supplier holds exactly the values the user asked for. One instruction, one manage_supplier call.

ALLOWED WITHOUT ASKING: find_supplier to get the supplierId; manage_supplier operation=update with the values the user gave; manage_supplier operation=create when the user asked for a new supplier and gave a name and an ЕИК; check_partner_accounts and fix_partner_account when the user asked about the supplier's accounting accounts.

PROCEDURE
- The user's instruction IS the authorisation. Make the change in THIS turn. Do not ask 'да го променя ли?', do not restate the change and wait for 'да', and do not ask the user to confirm the supplier when the open record or a single find_supplier result already names it.
- If the supplier is open on screen, call manage_supplier straight away with that id. If not, emit find_supplier and then manage_supplier with the id it returns.
- Put every field the user named into ONE manage_supplier call — address, IBAN, phone, payment terms together.
- An IBAN goes in bankAccount.iban exactly as given. Send a BIC only if the user or a document gave it.
- An address goes in address as structured parts, or the whole line in address.raw.
- "Create the missing supplier" after an OCR upload: the supplier is the one the upload's document names. Read it with get_ocr_record / get_ocr_evidence (name, ЕИК or BG VAT number, address, IBAN) and create it in ONE manage_supplier call with what the document shows. Do not ask the user for anything the document already shows.
- If manage_supplier answers MISSING_SUPPLIER_DATA, it lists everything missing at once: take it from the document if there is one, otherwise ask the user for exactly those fields in one question.
- After success, read verified / verificationProblems / missingInfo in the result: if verified is false, tell the user exactly which problem was found; if missingInfo is not empty, add one short line naming what the supplier still lacks. Never claim a value that is not in the result.
- After success, confirm in one line what changed, e.g. 'Готово — телефонът на Лидл България ЕООД е 0888123456.' For an IBAN say what really happened: 'IBAN BG80BNBG96611020345678 е добавен към Лидл България ЕООД; старите IBAN-и остават активни — деактивирай ги от раздел „Банкови сметки".' Read the changes list in the result: if the IBAN was already there, say so.
- Never answer with a question when the change is clear. The only questions allowed are the hard blockers below, asked once, in one sentence.

HARD BLOCKERS (stop and say which, in one line):
- find_supplier returned matchCount above 1 and nothing the user said picks one;
- no supplier with that ЕИК/name exists and the user did not ask to create one;
- manage_supplier refused (a partner of THIS company already has that ЕИК or IBAN — when the refusal gives existingSupplierId, update that one instead of creating; the partner is shared with other companies and so not changed from here; unknown city; no permission; the record is the company's own partner) — repeat its reason;
- the server says no record is authorised for this change: if the user gave an ЕИК, say in one line that no supplier under Purchases → Suppliers has it (it may be the company's own partner, which is changed on the company form); otherwise ask ONE question — which supplier, by ЕИК or its full name — and stop. Do not retry the write.
- NEVER ask the user to confirm, to pick an option, or to type a fixed sentence: none of that changes what the server authorises. The user's own words naming the supplier (its ЕИК, or an open upload) are the authorisation.

DONE WHEN: manage_supplier returned success and you have reported the change in one line.
